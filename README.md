# Halyk AI Challenge — AI-агент для проверки ковенантов

Агент читает кредитные договоры, банковские транзакции, аудиторские примечания
и KYC-досье, чтобы определить статус (COMPLIANT/BREACH) финансовых ковенантов
для 12 заёмщиков, и собирает результат в `submission.json`.

## Установка

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

## Настройка API-ключа

`term_extractor` поддерживает три backend'а, выбирается автоматически по тому,
какая переменная окружения установлена (приоритет сверху вниз):

```bash
export ANTHROPIC_API_KEY=sk-ant-...      # напрямую через Anthropic API
export OPENAI_API_KEY=sk-...             # напрямую через OpenAI API
export OPENROUTER_API_KEY=sk-or-...      # через OpenRouter
```

Ключ можно положить в `agent/.env` в формате `KEY=значение` (по одной паре на
строку). **pipeline.py не подгружает `.env` автоматически** — перед запуском
переменные нужно экспортировать в окружение процесса самостоятельно, например:

```bash
set -a && source agent/.env && set +a
```

## Запуск полного пайплайна

```bash
cd agent
python3 pipeline.py <путь_к_documents> <путь_к_master_ledger.csv> "<команда>" "<email>" submission.json
```

## Проверка результата (сверка с ground_truth, только для открытого датасета)

```bash
python3 eval/self_scorer.py submission.json <путь_к_ground_truth.json>
```

Скрипт печатает разбивку по компаниям/пунктам (`status`/`actual`/`evidence_txn_id`)
и никогда не выводит сырые значения из `ground_truth.json` — только баллы и
расхождения, чтобы не обесценивать смысл задачи.

## Архитектура

Пайплайн состоит из 10 модулей в `agent/`, выполняющихся последовательно:

1. `document_classifier` — определяет тип документа и `account_id` по содержимому PDF
2. `contract_selector` — выбирает актуальный (не черновик) договор на компанию
3. `scenario_mapper` — сопоставляет `account_id` со `scenario_id` (P1–P10, B1, B4) через леджер
4. `term_extractor` — LLM извлекает условия ковенантов 6.1/6.2/6.3 из текста договора
5. `transaction_analyzer` — классифицирует транзакции (CapEx/OpEx/Rent/Revenue/Payroll/Utilities/Insurance/Tax/Interest) по ключевым словам в описании
6. `kyc_linker` — извлекает связанные стороны из KYC-досье (порог голосующих прав читается из текста каждого досье, а не фиксирован) для расчёта 6.3
7. `audit_adjuster` — применяет cut-off корректировки из аудиторских примечаний
8. `computation_engine` — детерминированно считает `actual`-значения по классифицированным транзакциям (без LLM); диспетчеризация по ключевым словам в `metric_name` + `formula_description`
9. `evaluator` — сравнивает `actual` с порогом договора, определяет `status`
10. `pipeline.py` — оркестрирует всё вышеперечисленное, собирает `submission.json`

Плюс `schemas.py` — общие Pydantic-модели (контракт между модулями) и
`eval/self_scorer.py` — независимый скрипт сверки с `ground_truth.json`.

Принцип: LLM используется только для понимания текста документов (`term_extractor`).
Все расчёты, классификация транзакций и сравнения с порогом — чистый
детерминированный Python.

## Известные ограничения

- **Мультивалютность не поддерживается.** Транзакции не в базовой валюте пункта
  (обычно не USD) полностью исключаются из расчёта — курс конвертации нигде не
  задан в исходных документах и не подтягивается извне.
- **9 из 36 условий по датасету `computation_engine` сознательно не считает**,
  а явно возвращает причину вместо числа — для формул, требующих источник
  данных, которого нет в текущих файлах: консолидированная отчётность группы
  (капитальные затраты группы), данные казначейства по начисленным-но-неуплаченным
  налогам, список «Неограниченных дочерних организаций» из KYC, программа
  выходных пособий персонала «как раскрыто в примечаниях к отчётности».
- **`evidence_txn_id` никогда не заполняется** (всегда `null`) — `computation_engine`
  возвращает только агрегированную сумму, без привязки к конкретной транзакции-доказательству.
- **`term_extractor` (LLM) не гарантирует стабильное имя метрики** между
  запусками разных моделей/версий, даже при `temperature=0`. Диспетчеризация
  в `computation_engine` ищет ключевые слова и в `metric_name`, и в
  `formula_description` (она стабильнее) — это эвристика, а не строгая схема,
  и на новых формулировках может ошибаться.
- **`kyc_linker` — regex под конкретный формат** таблицы «Организация / Доля
  голосующих прав» и формулировку порога «владеет XX% и более». На датасете
  найдены и учтены варианты с запятой/точкой/кавычками вокруг названия
  компании, но парсер не универсален. У части компаний в датасете (например,
  P2) в KYC-файлах вообще нет таблицы владения, у части (например, P6) нет ни
  одного KYC-документа — это ограничение исходных данных, не кода.
- **Пустые/невалидные значения `amount`** в леджере пропускаются с явным
  warning, транзакция не участвует в расчёте, но пайплайн не останавливается.
- **Разный ковенантный период внутри одной компании** (например, один пункт —
  только за квартал, остальные — за год) детектируется и явно выводится как
  warning, но `computation_engine` использует период первого извлечённого
  пункта компании для отбора транзакций во всех расчётах этой компании — окно
  не пересчитывается отдельно под каждый пункт.
- **Разбор Статьи 6** в `term_extractor` полагается на характерный для этого
  датасета формат PDF (заголовок раздела отличается от строки оглавления
  наличием тире после номера статьи) — не универсален для произвольных
  договоров с другим форматированием.
